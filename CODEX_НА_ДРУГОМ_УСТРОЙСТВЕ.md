# Передача контекста Codex: Fauxlore на VPS

**Снимок состояния:** 3 ноября 2026 года (Europe/Moscow).
**Цель:** дать Codex на другом компьютере точную отправную точку. Считать нижеприведённые факты актуальным подтверждённым состоянием; перепроверять только то, что нужно для конкретной задачи.

## Коротко: что сейчас работает

- Игровой сайт: **https://sixiemeterre.ru**. Он обслуживается VPS `89.125.38.213` (Ubuntu 24.04). Старый адрес GitHub Pages `https://hookerslayer.github.io/fauxlore/` теперь содержит только перенаправление на сайт VPS (коммит `06e9b3b`).
- Рабочая база данных расположена **на том же VPS**: PostgreSQL 17, порт `5433`, база `fauxlore_production_candidate`. Публичный сайт подключается к ней по внутреннему API.
- PostgreSQL, PostgREST и внутренние Python API привязаны к loopback (`127.0.0.1`). Порт PostgreSQL не выставлен напрямую в интернет. Пользователь сайта обращается к данным через HTTPS/Nginx и серверные API.
- Это перенесённый снимок базы Supabase, а не продолжающая работать база Supabase и не двусторонняя синхронизация. Пользователь явно сказал, что свежесть относительно Supabase проверять не нужно; GitHub Pages отключена.
- Владелец завершил настоящий Google OAuth на `sixiemeterre.ru`. В браузере загрузились карта, раздел государства и экономика. Личная браузерная сессия была оставлена активной.
- Никакие игровые данные в ходе последних проверок не изменялись. Единственная production-активность при OAuth — обычная серверная сессия входа.

## Важное объяснение несоответствий в репозитории

Некоторые старые документы описывают более раннюю стадию (только Supabase/GitHub, тестовый VPS или OAuth, ещё не подключённый к production). Они устарели. В частности, `ДЛЯ CODEX.md`, `vps/README.md`, отдельные ранние абзацы `VPS_ПЛАН_ЗАПУСКА.md` и комментарий-маркер `CANDIDATE-NOT-LIVE.txt` могут утверждать, что VPS — только preview или ещё не публичный.

Текущий deployment был собран как отдельный bundle; скрипт `tools/build_vps_production_candidate.py` записывает в **bundle** `backend: 'vps-postgrest'`. Исходный корневой `app-config.js` может по-прежнему содержать Supabase backend и не доказывает, что production на GitHub/Supabase. Активная Nginx-конфигурация и развернутый bundle находятся на VPS. Не собирать/переключать релиз по догадке: этот build-скрипт отказывается перезаписывать существующий локальный каталог `.local/fauxlore-production-candidate`, а его текстовый маркер «not live» исторический и не отражает фактическое переключение.

Для дальнейшей работы источники истины читать в таком порядке:

1. Этот файл — передача текущего контекста и безопасные ограничения.
2. `AGENTS.md` — постоянные правила разработки.
3. `VPS_ПЛАН_ЗАПУСКА.md` — этапы, статус и порядок.
4. `vps/PERFORMANCE_TODO.md` — открытая проблема медленных запросов.
5. `vps/OPERATIONS_BACKUP.md` — процедура бэкапов и восстановления.
6. `git status --short` и фактическая активная конфигурация VPS — перед изменением файлов/сервисов.

## Архитектура production

```text
Браузер пользователя
  └─ HTTPS sixiemeterre.ru (Nginx, 80/443; HTTP и www → HTTPS apex)
       ├─ статический bundle из /opt/fauxlore/releases/candidate-20261103
       ├─ /auth/          → 127.0.0.1:18181 (Google OAuth и сессии)
       ├─ /api/rpc/       → 127.0.0.1:18186 (session bridge → PostgREST)
       └─ /api/projection/→ 127.0.0.1:18183 (серверные проекции/расчёты)
                              └─ PostgREST 127.0.0.1:18185
                                   └─ PostgreSQL 127.0.0.1:5433
                                        └─ fauxlore_production_candidate
```

На последней короткой проверке активная ссылка Nginx указывала на `/etc/nginx/sites-available/fauxlore-production-candidate`. Службы были активны и включены в автозапуск:

- `nginx`
- `fauxlore-auth-production.service` — `127.0.0.1:18181`
- `fauxlore-rpc-production.service` — `127.0.0.1:18183`
- `fauxlore-postgrest-production.service` — `127.0.0.1:18185`
- `fauxlore-postgrest-bridge-production.service` — `127.0.0.1:18186`
- `fauxlore-db-backup-production-candidate.timer`

Внешне подтверждены HTTPS apex `200`, HTTP → HTTPS и `www` → `https://sixiemeterre.ru/` (оба `301`). TLS, `nginx -t`, reload и Google OAuth уже проверялись. Не нужно повторять все эти проверки без причины.

## Как Codex со второго устройства может подключиться

### Предварительные условия

SSH должен запускаться **со второго устройства** к VPS по адресу `89.125.38.213`. Наличие этого Markdown или доступа к репозиторию само по себе не даёт серверных прав. Закрытый ключ текущего устройства не включён в репозиторий и не должен отправляться в чат, email или облачный документ.

На прежнем компьютере ключ был настроен по пути `%USERPROFILE%\.ssh\fauxlore_vps_ed25519`. Если на втором компьютере нет собственного разрешённого SSH-ключа, создайте на втором компьютере отдельную пару ключей в PowerShell:

```powershell
ssh-keygen -t ed25519 -a 64 -f "$env:USERPROFILE\.ssh\fauxlore_vps_ed25519" -C "fauxlore-second-device"
```

Задайте passphrase. На VPS добавляется **только публичный файл** `fauxlore_vps_ed25519.pub` (не файл без `.pub`). Добавление сделайте через уже доступное устройство/консоль провайдера, не удаляя прежние ключи и не перезаписывая `authorized_keys`. До выключения старого устройства проверьте вход со второго:

```powershell
ssh -i "$env:USERPROFILE\.ssh\fauxlore_vps_ed25519" root@89.125.38.213
```

Если SSH не работает, Codex не должен включать password login, открывать порт PostgreSQL наружу, менять firewall или угадывать реквизиты. Сначала использовать консоль AdminVPS/существующий рабочий доступ и установить отдельный публичный ключ безопасно.

### Безопасная работа с PostgreSQL

Внутри VPS соединение с PostgreSQL допустимо через локальную команду под системной ролью `postgres`, например:

```sh
sudo -u postgres psql -X -p 5433 -d fauxlore_production_candidate
```

Или с другого компьютера можно открыть SSH-туннель, не публикуя порт БД:

```powershell
ssh -i "$env:USERPROFILE\.ssh\fauxlore_vps_ed25519" -N -L 15433:127.0.0.1:5433 root@89.125.38.213
```

Затем подключаться PostgreSQL-клиентом к `127.0.0.1:15433`, указав имя базы и подходящую роль/секрет из защищённого хранилища. Не помещать пароль в командную строку, историю shell или handoff-файл. Если роли/пароля нет, не менять сетевую привязку PostgreSQL: сначала выяснить предусмотренный сервером способ доступа. Для просмотра на сервере предпочтительна `sudo -u postgres psql`.

### Что подготовить во втором рабочем пространстве

- Открыть именно репозиторий Fauxlore, а не старый локальный клон без этого handoff.
- Убедиться, что в рабочем дереве есть этот файл и актуальные `VPS_ПЛАН_ЗАПУСКА.md`, `vps/PERFORMANCE_TODO.md`, `vps/OPERATIONS_BACKUP.md`.
- Проверить `git status --short` до изменений. В этой копии есть незакоммиченные файлы/удаления, относящиеся к переносу; не делать `reset`, `clean`, автоматическое восстановление удалённых тестов или массовое форматирование.
- Handoff создан локально и не был закоммичен/отправлен в Git. Чтобы другой компьютер его увидел, файл нужно отдельно перенести либо включить в обычный review/commit/push-процесс. Не предполагать, что он уже есть в удалённом репозитории.

## Остаток работ и порядок

### 1. Производительность — открытая задача после запуска

Подробности и уже измеренные фазы — в `vps/PERFORMANCE_TODO.md`.

- После оптимизаций одиночный запрос finance на candidate занял около `2.58 s` (snapshot `2145 ms`, worker `435 ms`).
- При двух одновременных read-only finance-запросах оба получили HTTP `200`, но ожидавший слот запрос занял около `5.23 s` и провёл около `2.61 s` в очереди.
- В браузере экономика открылась без видимой ошибки; примерно 4 секунды — только грубое время между наблюдениями, это **не точное измерение**.
- Это не следует считать исправленной производительностью. Нужно локализовать медленные фазы SQL/API, проверить повторные запросы и конкуренцию на VPS с 1 CPU/2 ГБ, затем исправлять узкие места. Не увеличивать тайм-ауты как замену ускорению. Не запускать тяжёлую нагрузку на рабочей базе без отдельного безопасного плана.

### 2. Резервные копии

- Candidate backup настроен ежедневно около 03:00 UTC с random delay до 10 минут, хранит 7 последних файлов в `/var/backups/fauxlore/`.
- Свежий дамп после production OAuth: `fauxlore_production_candidate-20261102T222720Z.dump`. Локальная копия в `.local/vps-backups/`; SHA-256 совпал (`69938c30772f7759c61ea3350d625aa4cfe6ea512e6a79bfee0cbfd96063366b`). Дамп содержит приватные игровые данные: не читать его содержимое в чат, не коммитить и не передавать внешним сервисам.
- Архив candidate восстановлен ранее в отдельную recovery-БД; восстановление прошло. Новый свежий дамп после OAuth полностью повторно не восстанавливали.
- Наличие/успешность недельного backup у AdminVPS в личном кабинете не подтверждено. Проверить это, не выбирая платные опции без указания пользователя. Локальная копия на текущем ПК и архивы на том же VPS не защищают от потери обоих.

### 3. Production-права и устойчивость после перезапуска

- Базовый аудит подтвердил, что API-роли не superuser/BYPASSRLS и прямой `SELECT` клиента на игровые таблицы не найден; полный аудит прав **каждого RPC ещё не выполнен**.
- Точечно завершить read-only аудит `GRANT/REVOKE`, функций и разрешённых RPC по активной production-БД. Не выполнять старые test SQL целиком: некоторые файлы защищены именем staging-базы и могут отзывать общие права.
- Production units активны и enabled. Перезагрузка сервера не проверялась; не перезагружать публичный VPS спонтанно. Подготовить короткий план maintenance-window, backup/rollback и уведомление владельца, затем выполнять только при подходящем согласовании.

### 4. Краткий набор проверок и ограничения

- Пользователь просил свести проверки к самым общим. Гость: карта/календарь/стена; Google login владельца; собственный раздел государства/экономика; базовое ограничение доступа к чужому государству — уже проверены. Не повторять без причины.
- Не сравнивать данные VPS с Supabase и не запускать новый экспорт: пользователь явно отменил эту проверку и сообщил, что GitHub-страница отключена.
- Не создавать тестовые игровые операции на production и не менять существующие записи. Пользователь объяснил, что разовую новую запись мог сделать реальный игрок; сохранить live-состояние.
- Новый Google-пользователь реальным аккаунтом не проверен. Не проводить регистрацию в production без отдельной необходимости.
- Этап G (публичное переключение, TLS, домен, основные страницы, OAuth) завершён. План не сводится к G: оставшиеся пункты B/C/D/F указаны выше и в основном плане.

## Постоянные ограничения для Codex

- Серверная игровая логика, расчёты, валидация и проверка прав остаются на сервере. Не переносить авторитетные расчёты на клиент.
- Не раскрывать значения секретов, OAuth tokens/codes, cookies, private key, дампов, профилей/ID игроков или содержимое пользовательских игровых данных в чате/логах.
- Не открывать PostgreSQL наружу, не публиковать PostgREST `18185` напрямую, не отправлять клиенту JWT/service-role secrets.
- Не делать `git reset`, `git clean`, массовое удаление, commit или push без отдельного решения владельца. Старые тесты экономики пользователь разрешил удалить — файлы уже удалены; не восстанавливать их.
- Делать только небольшие необходимые проверки, соответствующие пользовательскому требованию о минимальном количестве проверок. Не запускать полную батарею тестов автоматически.
- Не говорить, что Supabase всё ещё production-база: production-домен обслуживается VPS. Не говорить, что VPS-база синхронизируется с Supabase: синхронизации нет.
