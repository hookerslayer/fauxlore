# Fauxlore — Supabase

Рабочий проект: `nfcshfpysnttmhvpbpax` («Fauxlore Map», eu-west-1).
Публичная конфигурация находится в `app-config.js`. Publishable key разрешено
хранить в клиенте; секретные ключи, пароль БД и OAuth Client Secret — нельзя.

## Устройство

Статический сайт (локальная сборка / GitHub Pages) → Supabase Auth и PostgREST RPC
`public.fauxlore_api(path, method, body, request_id)` → PostgreSQL.
Отдельный VPS, FastAPI и Edge Functions для этой версии не нужны.
Тайлы и WebGL остаются статическими файлами клиента.

Все прикладные таблицы находятся в закрытой схеме `fauxlore`, которая НЕ должна
включаться в список exposed schemas. RLS включён, прямые права браузерных ролей
на таблицы отозваны. Единственный публичный SQL wrapper — SECURITY INVOKER;
привилегированный dispatcher находится внутри закрытой схемы. Он разрешает
гостям только карту, health и пустой auth/me. Остальные маршруты проверяют
`auth.uid()`, подтверждённую Google identity и роль из таблицы accounts.
Роль из редактируемой пользователем metadata не используется.

Записи выполняются в одной транзакции. Повтор команды с тем же request_id
возвращает прежний результат; повтор с другим телом отвергается. Общего
глобального lock на все изменения карты нет. Локальные блокировки защищают
одну редактируемую провинцию, повтор одной команды и создание категории.

`schema.sql` — воспроизводимый исходник схемы/API. Прикладные таблицы создаются
через IF NOT EXISTS; функции обновляются CREATE OR REPLACE. Он не импортирует
данные и не назначает администратора. Не выполнять старый server/schema.sql
поверх Supabase: это схема прежнего локального сервера.
Зафиксированная начальная миграция: `migrations/20261020170218_initial_fauxlore_supabase.sql`;
эта же версия зарегистрирована в облачной истории миграций. Для последующих
изменений создавать новую миграцию, не переписывать применённую.

## Данные и перенос

20.10.2026 завершён импорт актуального игрового снимка.
Состав: 5716 провинций, 6818 назначений слоёв, 36 категорий, 4 аккаунта,
2 действующих маркера, 2 профиля настроек и 4 исходные настройки карты.
Два старых маркера типов temple/interest перенесены в archived_markers и скрыты
от API. Исторический чат и старые сессии/парольные хеши не активируются;
оригинальный workbook сохраняет полный исходный архив. Авторизация
принадлежит Supabase Auth; прежние сессии не активируются.

Закрытые файлы текущего переноса: `.local/supabase-migration/source.xlsx`,
`snapshot.json`, `sql/`. Они не входят в Git. Одноразовые инструменты импорта
удалены из рабочего проекта; их закрытая копия сохранена в
`.local/retired-sheets-20261020/` только для восстановления архива.

Каждая порция SQL идемпотентна, проверяет checksum и сравнивает импортированные
значения с типизированным источником. `import_batches` хранит квитанции.
Публичная карта закрыта, пока `_settings.migration_ready` не равен true.
После активации не повторять импорт старого снимка поверх живых данных.

На двух устройствах используется одна облачная база; Git переносит код, а не
локальную копию данных. Не восстанавливать старую локальную БД поверх облачной.
Исходный архив импорта не является источником актуальных правок.
Для резервирования Supabase нужны отдельные экспорты,
независимо от Git и возможностей бесплатного тарифа.

## Google-вход

Google OAuth client должен разрешать URI:
`https://nfcshfpysnttmhvpbpax.supabase.co/auth/v1/callback`.
В Supabase Authentication → Sign In / Providers включается Google и задаются
Client ID / Client Secret. В URL Configuration задаётся Site URL
`https://hookerslayer.github.io/fauxlore/` и разрешаются только нужные callback URL:

- `http://127.0.0.1:8004/supabase-return.html**`
- `https://hookerslayer.github.io/fauxlore/supabase-return.html**`

Суффикс нужен для одноразового параметра `?login=...`; можно настроить эквивалентные
более узкие правила. Для другого локального порта нужно отдельно добавить callback.
20.10.2026 владелец подтвердил сохранение обоих Redirect URLs и Site URL.
Client использует PKCE; popup возвращает только одноразовый code, origin/source
и случайный nonce проверяются перед обменом. Google Client Secret остаётся в Auth.

Первый Google-вход привязывает старый аккаунт по Google sub и сохраняет id/роль.
Для аккаунта без прежнего sub разрешена привязка по подтверждённому Gmail/Workspace
email; конфликт или чужая привязка отвергаются. Новому пользователю назначается player.

## Проверка и запуск

```powershell
powershell -ExecutionPolicy Bypass -File tools/start-supabase.ps1
```

Открыть http://127.0.0.1:8004/. Для публикации отдавать только каталог
`.local/supabase-site` или соответствующие статические файлы GitHub Pages.
Сборка не публикует сайт и не отправляет Git-коммит сама.

`test-api.sql` проверяет гостя, запрет чтения аккаунтов, привязку старого админа,
защиту от повышения роли через metadata, редактирование слоёв/провинции,
массовую правку, маркеры, настройки и идемпотентность. Все изменения и фиктивные
пользователи откатываются транзакцией. Запускать владельцем БД через MCP SQL.
Проверены также реальный Google-вход администратора и сохранение провинции 1332
без изменения её игровых значений из браузера.

Адвайзер RLS Enabled No Policy для закрытых таблиц ожидаем: доступ к данным
реализован только проверенным dispatcher. Это не повод открыть таблицы клиенту.
