# Производительность VPS — оптимизации, проверки и выпуск

Статус: **оптимизации выпущены в production 3 ноября 2026; базовые read-only smoke-проверки прошли. Устойчивость под нагрузкой и комфортная работа нескольких игроков не подтверждены.**

До выпуска повторная расширенная серия на отдельной нагрузочной копии дала шесть HTTP 200 за 1,395–2,897 мс; CPU VPS был занят на 100% во всех интервалах. Это не доказывает устойчивость или запас для дополнительных игроков. Затем изменения выпущены по подтверждённому плану; порядок, smoke-проверки и rollback описаны в `PERFORMANCE_RELEASE_REVIEW_2026-11-03.md`.

Продолжение 3 ноября 2026: подготовленные оптимизации Стены, дипломатии, показателей и финансов выпущены в production. Worker обновлён до миграций, восемь миграций применены одной транзакцией с parity-проверками, затем переключён статический каталог Nginx. Выполнена резервная копия БД и функций до изменений; живые данные не откатывались. Текущие проверки прошли, но запас по производительности остаётся малым, а расширенная устойчивость не подтверждена.

Исправлена подготовка входной страницы: корневой `index.html` остаётся редиректом GitHub Pages, а сборщики берут приложение из `vps/production-index.html`, соответствующего действующему релизу с обновлённой версией скрипта. Проверены тест сборщиков, локальная сборка и отдельный локальный production-candidate; публичный релиз не переключался.

Сокращены лишние запросы при открытии разделов государства игроком: больше не загружаются ставки сословий, которые присоединялись к локальной копии провинций, но нигде далее не использовались; уже полученные показатели повторно используются на обзоре и во вкладке экономики вместо повторного серверного запроса. Это уменьшает число вызовов и убирает последовательное ожидание, но экономия wall time для этого сценария отдельно не измерена. Последний статический candidate собран в `.local/fauxlore-production-candidate-state-load-2/`; live-сайт не менялся.

Финансовый projection уже рассчитывал показатели на сервере, но клиент отдельно запрашивал их параллельно. Теперь endpoint возвращает использованные сервером показатели вместе с прогнозом, и вкладка экономики использует единый ответ. Добавлен fallback для старого backend. Функциональные тесты проекции/worker и один изолированный API smoke прошли (HTTP 200, 1,428 мс; ответ содержит finance и indicators). Это не измерение браузерной загрузки или прироста скорости. Candidate с последними файлами создан в `.local/fauxlore-production-candidate-finance/`; production не менялся.

- На действующем сайте пользователь неоднократно видел тайм-ауты и незагруженные разделы. Причина пока не установлена: перенос на VPS сам по себе не доказывает, что проблема исчезнет.
- На изолированной копии VPS (1 CPU, 2 ГБ RAM) при открытии государства несколько запросов и расчётов запускались одновременно. Тестовый PostgREST с пулом из двух соединений возвращал `PGRST003` / HTTP 504, а параллельные расчёты получали HTTP 503 из-за единственного слота.
- В тестовой конфигурации пул увеличен до четырёх соединений, ожидание слота БД — до 30 секунд, а расчёты ожидают свободный слот до 20 секунд. После этого обзор, экономика и торговля открылись, но финансовая панель загружалась заметно долго. Эти изменения уменьшают вероятность немедленного отказа, **не устраняют установленную причину медленной работы** и могут увеличить время ожидания.
- Проверка проводилась с одним тестовым игроком. Несколько одновременных пользователей, пиковая нагрузка и стабильность при длительной работе не проверены. Не использовать результаты как подтверждение достаточности тарифа.

## Замеры и первое исправление (3 ноября 2026)

Измерения проведены на изолированной базе `fauxlore_restore_filtered`, одним тестовым игроком. В ответе API измеряется только длительность фаз; тела запросов, данные игрока, идентификаторы и токены не записываются.

- До исправления один запрос финансового прогноза вернул HTTP 200. Ожидание очереди — 5 мс, подготовка снимка — 7 550 мс, Node-расчёт — 413 мс. Внутри подготовки снимка: проверка аккаунта и список государств — 37 мс, показатели — 541 мс, торговые данные — 11 мс, закрытый источник проекции — 837 мс, финансовые входные данные — 6 113 мс.
- Изолированный повтор замеров функций показал: `military_api('snapshot')` занимал 6 774 мс; отдельный повтор контроля подходящих провинций — 4 664 мс; показатели — 573 мс; расчёт факторов каталога — 529 мс; содержание войск — 95 мс. Эти запросы запускались отдельно, поэтому их значения ориентировочные и не складываются как точная длительность endpoint.
- Причина долгой проверки контроля: для каждой провинции заново формировался полный JSON постоянных модификаторов государства. При проверке использовались тысячи провинций.
- Добавлена миграция `supabase/migrations/20261102215332_military_snapshot_control_fastpath.sql`. Она один раз вычисляет государственный модификатор контроля для военного снимка. Если у государства есть модификатор контроля с локальной областью действия, остаётся старый расчёт для каждой провинции.
- Перед изменением создана проверенная резервная копия тестовой базы на VPS: файл в `/root/fauxlore-backups/fauxlore-fastpath-before-20261103.dump`, формат прочитан `pg_restore` версии PostgreSQL 17. Дамп остаётся только на VPS и не включён в Git.
- Миграция выполнена в транзакции на изолированной базе и только если JSON-снимок одного тестового игрока до и после совпал. Транзакция завершилась успешно.
- После исправления повторный finance-запрос вернул HTTP 200. Ожидание очереди — 10 мс, подготовка снимка — 3 670 мс, Node-расчёт — 454 мс. Внутри снимка: аккаунт и список государств — 37 мс, показатели — 855 мс, торговые данные — 12 мс, закрытый источник — 860 мс, финансовые входные данные — 1 896 мс. Суммарная измеренная работа endpoint — около 4,1 с вместо 8,0 с в первом замере.
- Дополнительно выяснилось, что финансовый экран использует только `militaryData.upkeep_breakdown`, хотя worker загружал полный военный снимок с провинциями, каталогом войск и дипломатией. В `military_api` добавлено проверяемое владение государством действие `upkeep_snapshot`; полное `snapshot` осталось для военного интерфейса. Финансовый helper и worker переключены на компактный результат.
- Компактный результат сравнен с `upkeep_breakdown` полного снимка, затем один finance-запрос успешно выполнен через API. HTTP 200, около 2,5 с: ожидание очереди 3 мс, подготовка снимка 2 072 мс, Node-расчёт 414 мс; финансовые входные данные сократились до 401 мс.
- Два одновременных finance-запроса вернули HTTP 200, ошибок 503/504 не было. Один запрос ждал слот около 2,38 с и завершился за 4,89 с wall time; второй завершился за 2,38 с. Временные сессии удалены; после проверки активных сессий — 0.
- На отдельной `fauxlore_production_candidate` выполнен ещё один finance-запрос с временной сессией: HTTP 200, очередь 0 мс, снимок 2 145 мс, worker 435 мс (примерно 2,58 с в сумме). В снимке: auth/states 43 мс, indicators 724 мс, trade details 12 мс, projection source 815 мс, finance inputs 541 мс. Рядом в том же smoke-сценарии карта, календарь и стена для гостя вернули HTTP 200; собственный фин. обзор — 200; чужой штат — 403. Это один запрос на одной копии БД без параллельной нагрузки и без браузерного измерения; задержка в районе 2,5 с по-прежнему заметна и не подтверждает комфортную работу пользователей.
- На candidate выполнена одна пара одновременных read-only finance-запросов. Оба вернули HTTP 200, ошибок 503/504 не было; запрос без ожидания очереди завершился за 2,66 с, второй ждал слот 2,61 с и завершился за 5,23 с; пара целиком — 5,23 с. Это показывает отсутствие немедленного отказа при двух запросах, но задержка для ожидающего запроса остаётся заметной. Тест не моделирует длительную игру, множество пользователей или браузерные запросы целиком.
- После переключения публичная страница открылась в браузере, владелец завершил Google OAuth, а вкладка экономики в разделе государства отрисовалась без видимого тайм-аута или ошибки. Она появилась при следующем наблюдении примерно через 4 секунды; точная длительность рендеринга не измерялась. Это подтверждает только один браузерный сценарий.
- **Открытый performance follow-up после запуска:** на candidate одиночный finance-запрос занял около 2,58 с; из пары одновременных запросов второй ожидал слот и завершился за 5,23 с. Оба запроса получили HTTP 200. Поэтому очередь и долгие загрузки остаются проблемой для расследования, даже если выбранный пользовательский браузерный сценарий открылся без ошибки. Результаты не подтверждают комфортную работу при нескольких игроках. Не увеличивать тайм-ауты вместо поиска узкого места.

Следующий шаг после запуска: локализовать причины ожидания и медленной загрузки по существующим server timing-данным и коротким целевым замерам. Начать с наиболее долгих фаз БД, затем при необходимости посмотреть план запросов на копии и проверить конкуренцию за один CPU. Полную тестовую батарею не повторять. Перед масштабной нагрузочной проверкой определить минимальный безопасный сценарий и критерий вместе с владельцем; до этого не объявлять производительность исправленной.

## Выполнение оставшихся пунктов

1. **Профилирование — частично выполнено.** Server-Timing разбирает финансовый запрос до фаз БД и worker; последний изолированный smoke: 1 428 мс wall time, snapshot 970 мс, worker 450 мс. Ранее зафиксирован браузерный просмотр экономики и браузерная проверка дипломатии/Стены. Сеть и браузерный рендеринг новой вкладки экономики не измерены отдельно; это остаётся открытым пунктом.
2. **Повторы и горячие участки — выполнено для выявленных участков.** Подготовлены и проверены оптимизации стены, показателей, военного/дипломатического снимка, серверных показателей провинций и финансовых входов; устранены лишние клиентские запросы при открытии вкладок государства. Полные `EXPLAIN ANALYZE` всех оставшихся запросов не выполнялись, так как функциональные замеры уже выявили конкретные повторы, а VPS постоянно упирается в один CPU.
3. **Изолированная нагрузочная проверка — выполнено в согласованном ограниченном объёме.** Три пары по два read-only запроса, пауза 30 секунд; все HTTP 200, 1 395–2 897 мс, общая загрузка CPU 100%. Большая конкуренция, длительная стабильность и корректные метрики дискового I/O не подтверждены.
4. **Настройки пула/очереди и тариф — production не перенастраивались.** На копии проверялись настройки пула и ограничения ожидания; измерения не дают основания увеличивать тайм-ауты или обещать запас текущего тарифа. Выбор тарифа или изменение production-конфигурации требует отдельного решения владельца.
5. **Повторная проверка после исправлений — выполнена для выбранных сценариев.** Проекция/worker покрыты тестами; finance API проверен read-only smoke на изолированной копии. После выпуска публичные карта, календарь и Стена ответили HTTP 200. В авторизованном Codex IAB отрисовались экономика и дипломатия; production access log подтверждает HTTP 200 для `/api/projection/state` и `military_api`. Проверки parity и границ доступа прошли на изолированных копиях и в миграциях. Это один браузерный сеанс, он не измеряет устойчивость под нагрузкой.

## Выпуск в production (3 ноября 2026)

- До изменений сохранены архив PostgreSQL 17, схема с функциями/владельцами/ACL, три исходных worker-файла, Nginx-конфигурация. Старый статический каталог оставлен для быстрого возврата.
- Worker-файлы заменены атомарно в порядке `finance-projection.js` → `index.js` → `province_worker.mjs`. Затем восемь миграций `20261103144225`–`20261103153423` прошли одной транзакцией с `ON_ERROR_STOP`; все встроенные проверки совпадения завершились успешно.
- После `nginx -t` корень сайта переключён на `/opt/fauxlore/releases/performance-finance-20261103`; Nginx активен. Smoke после переключения: карта HTTP 200 (1 846 провинций, 546 мс), календарь HTTP 200 (14 мс), deferred-media Стена HTTP 200 (24 мс). Анонимный запрос дипломатического снимка получил HTTP 401, как ожидается по авторизации.
- В Codex IAB загрузились карта и публичная Стена с публикациями. После того как владелец завершил вход в браузере, экономика показала финансовый прогноз, дипломатия — список государств и отношений. Access log подтвердил HTTP 200 для финансового projection и `military_api`. Никаких игровых действий не выполнялось, время рендеринга не измерялось.
- После перехода service health: Nginx, PostgreSQL, RPC, PostgREST, bridge и auth active. Не выполнять полный DB restore для возврата кода: использовать документированный выборочный rollback из `PERFORMANCE_RELEASE_REVIEW_2026-11-03.md`.
